# 法律 AI 助手项目简历描述与技术实现说明

## 一、简历项目描述

项目名称：垂直领域法律 AI 助手

GitHub：https://github.com/Haowrite/law_agent.git

技术栈：LangGraph、FastAPI、LangChain、Milvus、BM25、Reranker、MySQL、SQLAlchemy、Redis、SSE、Locust、Conda

项目简介：

本项目是一款基于 LangGraph 构建的垂直领域法律 AI 助手，利用国家法律法规文档构建本地知识库，通过混合检索 RAG、引用可验证回答、深度研究模式和真流式 SSE 输出，为用户提供可追溯、可复核的法律咨询服务。系统重点优化了多用户并发场景下的 RAG 检索和 LLM 调用性能，并支持知识库文档的动态增删、检索和向量化更新。

核心工作：

1. 分层并发与性能优化：针对法律咨询中 LLM 调用慢、本地 RAG 检索阻塞的问题，设计分层并发策略，将 LLM API 调用与本地 RAG 检索分级处理；RAG 检索采用“异步队列 + 动态微批次”调度器，并引入显存异常捕获与重试机制，提升高负载下的服务连续性。Locust 压测表明，在 100 用户并发聊天场景下，系统平均响应时间从 36s 优化至 9s，提升约 75%。

2. 混合检索 RAG：搭建 BM25 + 稠密向量 Milvus 的双路召回架构，结合 RRF 融合排序与 Reranker 重排序，提高法律条文召回的准确性；针对口语化法律问题与专业法条之间的语义差异，使用查询改写和检索策略路由提升召回质量。在 DISC-law 数据集上，Recall@10 从 83% 提升至 91%。

3. 引用可验证回答与深度研究：设计统一 evidence 证据模型，将检索到的法条切片结构化为 citation_id、文档名、条文编号、摘录、内容哈希等字段；模型回答中必须使用 `[1]`、`[2]` 等编号引用证据，回答完成后由证据校验器检查引用编号是否存在、法律判断是否缺少引用。深度研究模式将复杂问题拆解为多个子问题，多轮检索证据后调用 LLM 生成结构化研究报告，并复用证据校验器校验报告可信度。

4. 真流式 SSE 输出：新增 FastAPI SSE 流式聊天接口，后端直接消费 LLM 的 `astream` token 流并实时推送给前端，解决传统“完整回答返回后再打字机展示”的假流式问题；SSE 事件拆分为 `status`、`content`、`metadata` 和 `[DONE]`，正文、检索状态、引用证据和校验结果分层传输，提升长回答和研究报告场景下的首 token 响应体验。

5. 上下文记忆管理：基于 Redis List 构建高频上下文缓存层，实施 Token 阈值滑动窗口算法；对滑出窗口的历史对话进行分批摘要压缩，并使用 MySQL 持久化摘要与原始消息，在模型有限上下文长度下提升长对话连贯性。数据库访问采用异步引擎，提高多用户并发下的读写能力。

6. 知识库管理模块：构建基于 MySQL + Milvus 的知识库管理模块，设计文档元数据、文档安全 key、条文切片 ID 与向量 ID 的映射机制；支持前端上传文档自动切分和向量化、按文档名搜索、预览、删除文档，并在更新时同步清理 MySQL、Milvus、BM25/RAG 缓存和服务端文件，保证知识库动态更新的一致性。

## 二、分项技术实现说明

### 1. 分层并发与性能优化

背景：

法律问答链路通常包含 LLM 推理、向量检索、BM25 检索、Reranker 重排序和数据库读写。早期实现中，多个用户请求会在本地模型检索和向量库访问上互相阻塞，导致高并发下平均响应时间明显升高。

使用技术：

- FastAPI：承载异步 HTTP 服务。
- asyncio：处理请求级异步调度。
- 进程池 / 线程池：隔离本地 RAG 检索任务。
- 动态微批次：合并短时间内到达的检索请求。
- Locust：模拟多用户并发压测。
- 显存异常捕获与重试：提高本地模型调用的稳定性。

实现方案：

- 将 LLM API 调用和本地 RAG 检索拆成不同并发层，避免单个慢任务阻塞整个聊天链路。
- 对 RAG 检索建立异步队列，请求进入队列后按短时间窗口聚合成 batch，统一送入本地向量检索和重排流程。
- batch 大小根据队列积压和模型资源动态调整，减少频繁单条推理带来的调度损耗。
- 对显存不足、模型推理失败等异常进行捕获，失败后降低 batch 或重试，保证高负载下服务不直接中断。
- 使用 Locust 对 100 用户并发聊天进行压测，对比优化前后的平均响应时间和错误率。

效果：

- 100 并发聊天平均响应时间从 36s 降至 9s。
- 高峰期请求不会因为单个 RAG 任务失败导致整体服务不可用。

### 2. 混合检索 RAG

背景：

法律问题具有强专业性，用户输入往往是口语化表达，例如“公司突然给我调岗合法吗”，而法律条文使用“用人单位、劳动合同、协商一致、劳动报酬”等专业表达。单纯向量检索容易漏掉关键词精确匹配，单纯 BM25 又难以理解语义相近表达，因此需要混合检索。

使用技术：

- Milvus：存储法律条文切片向量。
- Embedding 模型：将条文和问题编码为稠密向量。
- BM25：基于关键词的稀疏召回。
- RRF：融合 BM25 和向量检索结果。
- Reranker：对候选条文进行语义重排序。
- LangChain Tool：将 RAG 检索封装为 Agent 可调用工具。

实现方案：

- 法律文档入库时先按条文和片段进行切分，生成稳定的条文 ID 和 metadata。
- 对每个切片生成 embedding，并写入 Milvus；同时构建 BM25 索引用于关键词召回。
- 用户提问后，系统同时执行 BM25 检索和 Milvus 向量检索。
- 使用 RRF 将两路结果融合，既保留关键词命中的精确性，也保留向量语义召回能力。
- 对融合后的候选条文调用 Reranker，根据“问题-条文”相关性重新排序。
- 最终返回完整条文文本、已检索 ID 和结构化 evidence，为回答引用和证据校验提供基础。

效果：

- DISC-law 数据集 Recall@10 从 83% 提升至 91%。
- 对口语化问题、条文关键词和语义相近问题的召回更稳定。

### 3. 引用可验证回答与深度研究

背景：

法律 AI 回答最大的风险不是“说得不流畅”，而是“结论无法核验”。如果模型只说“根据相关法律规定”，用户无法知道引用来自哪份文档、哪一条、哪段原文。复杂问题还需要多角度研究，普通单轮问答难以覆盖法律依据、适用条件、救济路径和风险例外。

使用技术：

- LangGraph：承载普通问答 Agent 流程。
- RAG evidence 模型：统一证据结构。
- FastAPI：返回 citations 和 verification。
- LLM：生成引用编号回答和深度研究报告。
- 规则校验器：检查引用有效性和缺引用风险。
- Markdown：渲染研究报告。

实现方案：

- 设计 evidence 数据结构，字段包括 `citation_id`、`doc_key`、`chunk_id`、`filename`、`article`、`source_label`、`excerpt`、`content_hash` 和 `score`。
- RAG 检索不再只返回纯文本，而是同时返回结构化证据列表。
- Prompt 中将证据格式化为 `[证据1] 来源 + 原文摘录`，要求模型回答法律结论时使用 `[1]`、`[2]` 引用。
- 回答完成后调用证据校验器：
  - 检查回答中的引用编号是否存在。
  - 检查带有“应当、不得、可以、赔偿、仲裁、起诉、期限”等法律判断关键词的句子是否缺少引用。
  - 输出 `passed`、`warning` 或 `failed` 状态。
- 深度研究模式采用异步 job：
  - 创建研究任务并返回 job_id。
  - 将问题拆解为“法律依据、适用条件、救济路径、风险例外”四类子问题。
  - 每个子问题分别执行 RAG 检索并收集 evidence。
  - 对 evidence 去重并重新编号。
  - 调用 LLM 生成包含问题概述、核心结论、法律依据、判断要点、风险与行动建议的研究报告。
  - 对研究报告再次执行证据校验。

效果：

- 用户可以从回答中的 `[1]` 直接查看证据来源、摘录和内容哈希。
- 深度研究报告不再是简单拼接检索结果，而是由 LLM 基于多轮证据进行综合分析。
- 系统能自动提示引用缺失和引用编号错误，提高法律回答可信度。

### 4. 真流式 SSE 输出

背景：

长法律回答和深度研究报告生成时间较长。如果后端等待完整答案生成后一次性返回，前端即使做打字机动画，也只是视觉上的“假流式”，用户仍然要等待完整结果生成完成后才能看到第一段内容。

使用技术：

- FastAPI `StreamingResponse`：实现 SSE HTTP 流式响应。
- LLM `astream`：消费模型真实 token 流。
- JavaScript Fetch + ReadableStream：前端逐块读取 SSE 数据。
- SSE 事件协议：拆分状态、正文和元数据。

实现方案：

- 新增 `POST /api/chat/stream` 接口，保留原 `/api/chat` 作为兼容兜底。
- 接口先校验用户、会话权限和消息长度，然后检索知识库 evidence。
- 构造包含对话上下文、用户问题和编号证据的 prompt。
- 后端通过 LLM 的 `astream` 方法获取 token chunk，每获得一个 chunk 就发送一条：

```text
data: {"type":"content","content":"..."}
```

- 检索和生成阶段发送 `status` 事件，前端不把它拼进回答正文。
- 完整回答生成后，后端保存用户消息和 AI 消息，再执行证据校验，并发送：

```text
data: {"type":"metadata","citations":[...],"verification":{...}}
data: [DONE]
```

- 前端只把 `content` 事件追加到聊天气泡；收到 `metadata` 后再渲染引用卡片和校验状态。
- 如果流式接口异常，前端回退到 `/api/chat`，保证旧链路仍可用。

效果：

- 用户可以在模型生成过程中实时看到回答内容。
- 引用证据和校验结果仍然在回答完成后结构化展示。
- 避免了“完整响应 + 前端打字机”的假流式体验。

### 5. 上下文记忆管理

背景：

法律咨询常常需要多轮追问，例如用户先描述事实，再补充合同内容、工资情况、证据材料。直接把全部历史对话塞进模型会导致 token 超限，也会降低响应速度。

使用技术：

- Redis List：缓存未摘要消息、已摘要消息和摘要内容。
- MySQL：持久化原始对话和摘要。
- SQLAlchemy 异步引擎：提升并发读写性能。
- Token 阈值滑动窗口：控制上下文长度。
- LLM 摘要模型：压缩历史对话。

实现方案：

- 新消息先写入 MySQL，再写入 Redis 高频缓存，保证持久化优先。
- Redis 中维护未摘要消息列表、摘要列表和 token 计数 metadata。
- 当未摘要消息 token 超过阈值时，后台触发摘要压缩。
- 将最早一批未摘要消息送入摘要模型，生成“用户咨询问题 + 解决方案摘要”。
- 摘要写入 MySQL 后，再从 Redis 未摘要列表移除对应消息，避免数据库失败造成缓存状态错误。
- 模型调用时组合“历史摘要 + 近期未摘要消息”，在有限 token 下保留核心上下文。

效果：

- 支持长对话连续咨询。
- 减少重复传输历史消息造成的 token 浪费。
- 异步数据库读写提升多用户会话并发能力。

### 6. 知识库管理模块

背景：

法律法规会更新，用户也可能上传自己的合同、规章或内部材料。知识库如果只能离线构建，无法满足动态维护需求。文档删除时还要同步清理文件、数据库和向量库，否则会出现旧条文残留。

使用技术：

- FastAPI UploadFile：处理文档上传。
- MySQL：存储文档与条文切片元数据。
- Milvus：存储向量。
- BM25/RAG cache：维护检索索引缓存。
- 文档安全 key：避免前端暴露服务端绝对路径。
- 前端文档库 UI：支持搜索、预览、上传和删除。

实现方案：

- 上传文档后保存到服务端文档库目录，并进行文本解析、清洗和切分。
- 切分结果写入 MySQL，记录文档名、文档 key、条文 ID、切片内容和文件状态。
- 同步生成 embedding 并写入 Milvus，metadata 中保存切片 ID 和来源信息。
- 前端搜索文档时只传递文档名关键词，后端返回文档名、切片数、预览内容和安全 `doc_key`，不返回服务器绝对路径。
- 删除文档时以后端 `doc_key` 定位文档，依次删除：
  - 服务端文件。
  - MySQL 文档元数据和条文映射。
  - Milvus 中对应向量。
  - RAG cache / BM25 相关缓存。
- 重新创建或重新向量化文档时，先清理旧记录，再写入新记录，避免旧向量和旧条文残留。

效果：

- 知识库可以通过前端动态维护。
- 删除和重建文档后，MySQL、Milvus 和缓存保持一致。
- 前端不泄露服务端真实路径，降低安全风险。
