# 法律 AI 助手项目简历描述与技术说明

## 1. 简历可用版本

项目名称：法律垂直领域 AI 助手

GitHub：https://github.com/Haowrite/law_agent.git

技术栈：LangGraph、FastAPI、LangChain、Milvus、BM25、Reranker、MySQL、SQLAlchemy、Redis、SSE、Locust

项目描述：

基于 LangGraph 和 RAG 构建法律垂直领域 AI 助手，使用法律法规文档构建本地知识库，支持多轮法律咨询、条文引用溯源、深度研究报告、知识库动态维护和流式问答。系统围绕法律问答的召回准确率、回答可信度和并发响应性能做了专项优化，并通过 MySQL、Milvus、Redis 分别管理业务数据、向量数据和会话上下文缓存。

核心工作：

1. 分层并发与 RAG 性能优化：将 LLM API 调用、本地 RAG 检索、数据库读写和缓存更新拆分为不同执行层，避免单个慢环节阻塞完整请求链路；针对本地检索和重排序任务设计“异步队列 + 动态微批次”调度流程，并加入显存异常捕获、降级重试和批量任务恢复机制。使用 Locust 在 100 用户并发聊天场景下压测，平均响应时间从 36s 降至 9s，性能提升约 75%。

2. 混合检索 RAG：搭建 BM25 + Milvus 稠密向量双路召回架构，文档切片同时写入关键词索引和向量索引，检索阶段使用 RRF 融合稀疏检索与向量检索结果，再通过 Reranker 对候选条文进行精排；同时对口语化咨询问题进行查询改写，缩小用户表达与法律条文表述之间的语义差距。在 DISC-law 数据集上，Recall@10 从 83% 提升至 91%。

3. 引用可验证回答与深度研究：设计 evidence 证据模型，将 RAG 结果结构化为引用编号、文档名、条文编号、摘录、内容哈希等字段；回答生成时要求模型使用 `[1]`、`[2]` 标注依据，回答后通过证据校验器检查引用编号是否有效、法律判断是否缺少引用。深度研究模式将复杂问题拆解为法律依据、适用条件、救济路径、风险例外等子问题，多轮检索后调用 LLM 生成结构化研究报告，并复用证据去重和校验逻辑输出可信度提示。

4. SSE 真流式问答：新增 FastAPI `StreamingResponse` 流式接口，后端直接消费 LLM `astream` 输出，并以 SSE 事件实时推送到前端；将流式事件拆分为 `status`、`content`、`metadata` 和 `[DONE]`，正文 token、生成阶段、引用证据和校验结果分层传输，使用户在长回答场景下先看到首段内容，再接收完整证据元数据。

5. 上下文记忆管理：基于 Redis List 构建会话上下文缓存，使用 Token 阈值滑动窗口控制输入长度；对超出窗口的历史对话进行分批摘要压缩，并将原始消息和摘要结果持久化到 MySQL。数据库访问采用 SQLAlchemy 异步引擎，会话列表接口使用 `LEFT JOIN + GROUP BY` 一次性聚合消息数，摘要状态更新使用批量 `UPDATE`，减少 N+1 查询和 ORM 对象加载开销。

6. 知识库管理模块：构建 MySQL + Milvus 的知识库更新链路，维护文档元数据、条文切片 ID、向量 ID 和安全文档 key 的映射关系；支持前端上传文档、自动切分向量化、按文档名检索、预览和删除，并在删除或重建时同步清理 MySQL、Milvus、BM25/RAG 缓存和服务端文件，保证文档库、向量库和检索缓存的一致性。

## 2. 技术实现说明

### 2.1 项目背景与应用价值

#### 为什么做这个项目

法律咨询有三个典型特点：

1. 问题表达口语化。用户常说“公司突然调岗怎么办”“借钱不还怎么起诉”，但法律条文使用的是“劳动合同变更”“诉讼时效”“举证责任”等规范表达。
2. 答案必须有依据。法律场景不能只给一个看起来合理的结论，还要能说明依据来自哪份法规、哪一条、哪段原文。
3. 法规和知识库会变化。法律法规、公司制度、合同模板、案例材料都可能更新，系统需要支持知识库动态维护，而不是一次性离线构建。

因此，这个项目不是简单做一个聊天机器人，而是把大模型接入法律知识库、证据引用、会话记忆、知识库更新和并发服务能力，形成一个可落地的法律问答系统。

#### 应用价值

这个系统适合以下场景：

- 普通用户的基础法律咨询：快速了解某个问题可能涉及的法律依据、处理路径和风险点。
- 企业内部制度和合同问答：把公司制度、合同模板、合规文件上传到知识库后，员工可以基于内部资料提问。
- 律师或法务的检索辅助：对复杂问题先做多角度检索和初步报告，减少人工查找条文的时间。
- 法律知识库管理：支持上传、搜索、预览、删除和重新向量化文档，使知识库可以持续更新。

项目的重点不是替代律师，而是把“检索依据、整理信息、生成初稿、提示风险”这些耗时环节自动化。

#### 为什么不直接问大模型

直接问通用大模型有几个问题：

1. 知识不一定及时。模型参数里的知识有时间边界，无法保证覆盖最新法规、内部制度或用户上传的文档。
2. 引用不可控。模型可能说“根据相关法律”，但不一定能给出系统知识库中真实存在的条文来源。
3. 容易产生幻觉。法律场景里，编造法条编号、扩大适用条件或忽略例外都会带来风险。
4. 无法接入私有文档。企业合同、内部规章、用户自己的材料不会天然存在于通用模型里。
5. 缺少业务系统能力。真实应用还需要用户系统、会话持久化、知识库更新、权限控制、并发处理和前端交互。

本项目用 RAG 把大模型的生成能力限制在可检索证据范围内：先从知识库查依据，再让模型基于依据回答，并在回答后进行证据校验。这样比“直接问模型”更适合法律这种高准确性、高可追溯要求的场景。

#### 为什么使用这些技术

- LangGraph：法律问答不是单次模型调用，需要“判断是否检索 -> 调用 RAG -> 基于证据回答 -> 校验引用”的流程编排。LangGraph 适合把多步骤 Agent 流程做成状态机，便于维护和扩展。
- FastAPI：后端接口需要同时支持普通 HTTP、文件上传、后台任务和 SSE 流式响应。FastAPI 原生支持异步接口，适合构建这类 AI 服务。
- Milvus：法律条文需要向量检索，Milvus 用来存储切片 embedding，并支持按相似度召回候选条文。
- BM25：法律文本里关键词很重要，例如“仲裁时效”“协商一致”“劳动报酬”。BM25 能补足向量检索对精确关键词不敏感的问题。
- Reranker：BM25 和向量召回拿到的是候选集，Reranker 用来进一步判断“问题和条文是否真的相关”，提升最终证据质量。
- MySQL / SQLAlchemy：用户、会话、消息、文档元数据和条文映射属于结构化业务数据，需要关系型数据库持久化；SQLAlchemy 异步引擎用于提升并发读写能力。
- Redis：多轮对话上下文读写频繁，Redis List 适合缓存近期消息、摘要和 token 计数，减少每轮都查 MySQL 的成本。
- SSE：聊天回答是服务端持续向前端推送，SSE 比 WebSocket 更轻量，适合 LLM token 单向流式输出。

### 2.2 整体架构

系统采用前后端分离思路实现，前端由原生 HTML/CSS/JavaScript 构建交互界面，后端使用 FastAPI 提供聊天、知识库管理、深度研究和会话接口。

核心数据流：

```text
用户问题
  -> FastAPI 路由鉴权与参数校验
  -> Redis / MySQL 读取会话上下文
  -> LangGraph 编排问答流程
  -> RAG 工具执行 BM25 + Milvus 混合检索
  -> Reranker 对候选条文重排序
  -> LLM 基于证据生成回答
  -> 证据校验器检查引用
  -> 前端展示回答、引用证据和校验状态
```

主要存储分工：

- MySQL：用户、会话、消息、摘要、文档元数据、条文切片映射。
- Redis：高频会话上下文缓存、未摘要消息列表、摘要列表、token 计数。
- Milvus：法律条文切片向量、向量检索 metadata。
- 本地文件系统：上传文档和法律文档源文件。
- RAG 缓存文件：保存文档切分结果和 BM25 构建所需数据。

### 2.2.1 数据库与存储结构设计

| 字段 | 类型 | 约束 | 含义 |

| `doc_id` | `VARCHAR(64)` | 非空 | 文档 ID，用于把同一文档下的多个切片归组。 |

#### Redis Key 结构

| Key | 类型 | 字段 / 内容 | 含义 |
|-----|------|-------------|------|
| `session:{session_id}:unsummarized` | `List` | JSON 消息对象 | 保存近期未摘要消息，模型上下文优先读取。 |

### 2.2.2 性能优化与后续优化设计

#### 已落地优化

1. 会话列表 N+1 查询优化：原逻辑先查用户会话，再逐个会话查询消息数；现在改为 `LEFT JOIN + GROUP BY` 一次聚合出每个会话的消息数，用户会话越多，数据库往返减少越明显。
2. 摘要状态批量更新：原逻辑先加载消息 ORM 对象，再循环设置 `is_summarized=True`；现在改为单条批量 `UPDATE`，减少对象加载、Python 循环和会话内存占用。
3. Redis 上下文缓存：高频上下文读取优先走 Redis List，避免每轮对话都从 MySQL 全量加载历史消息。
4. Token 滑动窗口和摘要压缩：未摘要 token 超阈值后，只压缩早期消息，保留近期原文，控制 LLM 输入长度和调用成本。
5. RAG 缓存刷新：文档新增、删除或重建后刷新 BM25/RAG 缓存，避免检索阶段重复从 Milvus 全量冷加载。
6. 知识库一致性清理：文档删除或重建时同步处理服务端文件、MySQL 映射、Milvus 向量和 RAG 缓存，避免旧数据残留影响回答。
7. SSE 真流式：后端直接消费 LLM `astream`，降低长回答场景下首段内容等待时间。

#### 可继续设计的优化

1. 联合索引优化：为 `chatmessage(session_id, timestamp)` 和 `summarymessage(session_id, timestamp)` 增加联合索引，加速会话详情、上下文恢复和摘要加载。
2. 文档搜索优化：将 `doc_article.doc_abs_path LIKE '%keyword%'` 升级为独立文档元数据表，维护 `filename` 字段并加索引；数据规模继续增长时可使用 MySQL FULLTEXT 或 Elasticsearch。
3. 深度研究任务持久化：将当前研究任务状态从内存 job store 升级到 Redis 或 MySQL，支持服务重启后恢复任务进度。
4. Milvus 索引升级：小规模数据使用 `FLAT` 便于准确验证；大规模数据可切换为 `HNSW` 或 `IVF_FLAT`，用召回率和查询延迟压测选择参数。
5. RAG 结果缓存：对高频问题缓存 query rewrite、召回结果和 rerank 结果，减少重复 embedding 和重排序调用。
6. 文档增量索引：新增文档时只增量更新对应 BM25 分片和向量集合，避免每次更新后全量重建缓存。

### 2.3 分层并发与动态微批次

#### 背景

法律问答链路比普通聊天更长：一次请求可能包含会话读取、问题改写、向量检索、BM25 检索、Reranker 重排序、LLM 生成和数据库写入。早期链路中，本地 RAG 检索和重排序会阻塞请求，多个用户同时访问时平均耗时明显上升。

#### 技术选型

- FastAPI / asyncio：处理 HTTP 请求级异步并发。
- 线程池或进程池：隔离本地检索和重排序任务。
- 异步队列：缓冲并发检索请求。
- 动态微批次：将短时间窗口内的检索任务合并处理。
- Locust：压测 100 并发聊天场景。

#### 实现方案

1. 将请求链路拆成三层：LLM API 调用层、本地 RAG 检索层、数据库读写层。
2. RAG 检索请求不直接同步执行，而是进入异步队列。
3. 调度器按时间窗口和队列长度聚合请求，形成微批次。
4. 微批次统一执行 embedding、向量检索、BM25 召回和 Reranker 重排。
5. 如果显存异常或 batch 执行失败，捕获异常后降低批次规模或重试，避免一次失败影响整批服务。
6. 请求完成后再把结果按原请求顺序分发回对应用户。

#### 简历中怎么讲

可以说：“我把本地 RAG 检索从请求同步链路中拆出来，用异步队列做削峰，再用动态微批次减少本地模型重复调度开销。”

### 2.4 混合检索 RAG

#### 背景

法律咨询里用户表达通常很口语化，法律文档则是规范表述。比如用户说“公司突然把我调去外地合法吗”，条文里可能出现的是“用人单位与劳动者协商一致”“变更劳动合同约定内容”。只用关键词检索会漏掉语义相近问题，只用向量检索又可能错过精确法条关键词。

#### 技术选型

- Milvus：向量检索。
- BM25：关键词召回。
- RRF：融合两路召回结果。
- Reranker：对候选条文做精排。
- LangChain Tool：把检索能力封装成 Agent 工具。

#### 实现方案

1. 文档入库时按条文切分，生成稳定的条文 ID。
2. 每个切片写入两套索引：
   - Milvus：保存 embedding 向量和 metadata。
   - BM25：保存切片文本和关键词索引。
3. 用户问题进入 RAG 后，同时执行 BM25 和向量召回。
4. 使用 RRF 融合两路排名，避免某一路检索结果过度主导。
5. 对融合结果调用 Reranker，按“问题和条文是否真正相关”重新排序。
6. 返回完整条文、已检索 ID 和 evidence 结构，供 LLM 引用。

#### RRF 是什么

RRF 全称 Reciprocal Rank Fusion，作用是融合多个检索器的排序结果。它不直接看分数绝对值，而看文档在每个检索器里的排名。例如某个条文在 BM25 排第 2、向量检索排第 6，它会比只在一路里排名靠后的条文更容易进入最终结果。

### 2.5 Evidence 证据模型

#### 背景

法律回答需要能核验来源。模型不能只说“根据相关法律”，系统必须告诉用户：这句话依据的是哪份文档、哪一条、哪段摘录。

#### Evidence 字段解释

```json
{
  "citation_id": 1,
  "doc_key": "安全文档标识",
  "chunk_id": "条文切片ID",
  "filename": "劳动合同法",
  "article": "第三十五条",
  "source_label": "劳动合同法 / 第三十五条",
  "excerpt": "用人单位与劳动者协商一致，可以变更劳动合同约定的内容。",
  "content_hash": "a1b2c3d4e5f6g7h8",
  "score": 0.87
}
```

字段含义：

- `citation_id`：引用编号。模型回答里的 `[1]` 对应 `citation_id=1` 的证据。
- `doc_key`：文档安全标识。前端删除、预览文档时使用它定位文档，避免暴露服务器绝对路径。
- `chunk_id`：条文切片 ID。用于定位 Milvus 和 MySQL 中的具体条文片段。
- `filename`：文档名，用于前端展示。
- `article`：条文编号或片段编号，例如“第三十五条”。
- `source_label`：面向用户展示的来源标题。
- `excerpt`：证据摘录，只展示短片段，不把整篇文档直接暴露到前端。
- `score`：检索或重排序分数，用于排查召回质量。

#### content_hash 是什么

`content_hash` 是证据摘录或条文内容经过哈希算法计算出的短指纹。它不是加密后的原文，也不能反推出原文。

在项目里的作用：

1. 判断证据是否重复：多轮检索可能召回同一条法条，内容哈希相同就可以去重。
2. 做证据完整性标识：前端展示某条证据时，可以看到它对应的内容指纹，方便排查“引用编号没变但内容是否换了”。
3. 避免暴露原始路径：系统不需要把服务器路径发给前端，也能给证据一个稳定标识。

简单理解：

```text
原文：用人单位与劳动者协商一致，可以变更劳动合同约定的内容。
content_hash：这段文字的短指纹
```

只要原文内容变化，hash 基本也会变化；原文不变，hash 会保持稳定。

### 2.6 引用可验证回答

#### 背景

法律 AI 的可信度不只取决于回答是否流畅，还取决于结论能否追溯。为了降低模型“看起来有依据但实际没依据”的风险，系统把引用编号控制在 RAG 返回的 evidence 范围内。

#### 实现方案

1. RAG 工具返回 `text`、`retrieved_ids` 和 `evidences`。
2. Agent 将 evidence 格式化成 prompt：

```text
[证据1]
来源：劳动合同法 / 第三十五条
原文摘录：用人单位与劳动者协商一致，可以变更劳动合同约定的内容。
```

3. Prompt 要求模型回答时引用 `[1]`、`[2]`，不能引用不存在的编号。
4. 前端在回答气泡下展示“引用依据”卡片。
5. 用户点击引用卡片，可以查看来源、条文编号、摘录和内容哈希。

#### 这项能力的价值

- 面向用户：能看到回答依据，不是只看模型口头解释。
- 面向系统：后续可以继续做自动校验、证据对齐和引用质量评估。
- 面向面试：这是把 RAG 从“把文本塞给模型”升级成“结构化证据驱动回答”。

### 2.7 证据校验器

#### 背景

即使 prompt 要求模型引用证据，模型仍可能漏标引用，或者生成 `[8]` 这种不存在的编号。因此回答结束后要做一次确定性校验。

#### 实现方案

1. 用正则提取回答中的 `[n]` 引用编号。
2. 将编号和 evidence 列表中的 `citation_id` 对比。
3. 如果回答引用了不存在的编号，状态设为 `failed`。
4. 将回答按句号、问号、分号和换行切分。
5. 对包含法律判断关键词的句子做检查，例如：
   - 应当
   - 不得
   - 可以
   - 赔偿
   - 仲裁
   - 起诉
   - 期限
   - 责任
6. 如果法律判断句没有引用，状态设为 `warning`。
7. 前端展示校验状态和 warning 明细。

#### 为什么第一版用规则而不是 LLM

规则校验速度快、可测试、成本低，适合先覆盖“引用编号是否存在”和“明显缺引用”这类确定性问题。LLM 校验可以作为后续增强，用来判断“引用内容是否真的支持该结论”。

### 2.8 深度研究模式

#### 背景

复杂法律问题通常不是一个法条就能回答。例如“公司单方调岗是否合法”至少涉及合同约定、协商一致、工作地点变化、薪资变化、劳动者救济路径和举证风险。普通单轮问答容易回答得过粗。

#### 技术选型

- FastAPI BackgroundTasks：异步执行研究任务。
- 内存 job store：保存任务进度、阶段和结果。
- RAG 多轮检索：围绕多个子问题召回证据。
- LLM：基于证据生成研究报告。
- 证据校验器：校验研究报告引用质量。

#### 实现方案

1. 前端点击“深度研究”后，调用 `POST /api/research/start` 创建任务。
2. 后端生成 `job_id`，任务进入后台执行。
3. 系统将原问题拆为四类子问题：
   - 核心法律依据是什么？
   - 适用条件、构成要件或判断标准是什么？
   - 当事人可以采取哪些救济路径？
   - 有哪些风险、例外和注意事项？
4. 每个子问题分别执行 RAG 检索，收集 `text`、`retrieved_ids` 和 `evidences`。
5. 对 evidence 按 `content_hash` 去重，重新生成连续引用编号。
6. 调用 LLM 生成 Markdown 研究报告，结构包括：
   - 问题概述
   - 核心结论
   - 法律依据
   - 适用条件 / 判断要点
   - 风险与例外
   - 行动建议
   - 证据清单
7. 报告生成后执行证据校验。
8. 前端轮询任务状态，完成后把报告插入聊天区，并展示引用证据。

#### 和普通问答的区别

普通问答重视快速响应，适合简单咨询；深度研究重视覆盖面和结构化分析，适合复杂问题、争议判断和需要行动方案的场景。

### 2.9 SSE 真流式输出

#### 背景

LLM 生成长回答时，用户真正关心的是多久能看到第一段内容。系统因此新增 SSE 流式接口，让后端在模型生成过程中持续发送内容。

#### 技术选型

- FastAPI `StreamingResponse`
- LLM `astream`
- SSE 协议
- 前端 Fetch `ReadableStream`

#### 事件设计

```text
data: {"type":"status","stage":"retrieving","message":"正在检索知识库"}

data: {"type":"content","content":"根据"}

data: {"type":"content","content":"劳动合同法"}

data: {"type":"metadata","citations":[...],"verification":{...}}

data: [DONE]
```

各事件含义：

- `status`：告诉前端当前处于检索、生成等阶段，不拼进回答正文。
- `content`：LLM 实时生成的正文片段，前端追加到聊天气泡。
- `metadata`：回答完成后返回引用证据和校验结果。
- `[DONE]`：流结束标记。

#### 实现方案

1. 新增 `POST /api/chat/stream`。
2. 先进行用户、会话和消息长度校验。
3. 读取 Redis / MySQL 中的会话上下文。
4. 检索 evidence 并构造带证据的 prompt。
5. 调用 `main_llm.astream(...)` 获取模型实时输出。
6. 每收到一个 chunk，就立即发送一个 `content` SSE 事件。
7. 完整回答生成后，写入 MySQL 和 Redis。
8. 执行证据校验并发送 `metadata`。
9. 前端收到 `[DONE]` 后移除流式光标。

#### 为什么 metadata 不和 content 混在一起

引用证据和校验结果必须等完整回答生成后才能计算。如果提前发送，校验器拿不到完整答案；如果混在正文里，前端会把 JSON 当成回答展示。因此正文和元数据分事件传输。

### 2.10 上下文记忆管理

#### 背景

法律咨询经常是多轮对话，用户会不断补充事实和证据。系统需要保留上下文，但不能无限制把所有历史消息传给模型。

#### 技术选型

- Redis List：缓存高频会话消息。
- MySQL：持久化原始消息和摘要。
- SQLAlchemy async engine：异步数据库访问。
- Token 阈值滑动窗口：控制上下文长度。
- LLM 摘要：压缩早期对话。

#### 实现方案

1. 每轮对话先写 MySQL，再写 Redis。
2. Redis 保存未摘要消息、已摘要消息、摘要内容和 token 计数。
3. 未摘要内容超过阈值后，取最早一批消息生成摘要。
4. 摘要写入 MySQL 后，再更新 Redis 列表。
5. 模型调用时拼接“历史摘要 + 近期原文消息”。

#### 为什么先写 MySQL 再写 Redis

MySQL 是最终持久化数据，Redis 是缓存。如果先改 Redis 再写 MySQL，数据库失败会导致缓存和持久化状态不一致；先落库再刷缓存更容易保证恢复能力。

### 2.11 知识库管理模块

#### 背景

知识库需要支持动态更新。用户上传新文档后，要写入文件系统、MySQL、Milvus 和 RAG 缓存；删除文档时，也必须清理这些位置，否则检索结果里会出现已经删除的旧内容。

#### 技术选型

- FastAPI UploadFile
- MySQL 文档元数据表
- Milvus 向量库
- BM25 / RAG cache
- 安全文档 key
- 前端文档管理 UI

#### 实现方案

1. 上传文档：
   - 保存到服务端文档库。
   - 解析文本并切分条文。
   - 写入 MySQL 文档和条文映射。
   - 生成 embedding 并写入 Milvus。
   - 刷新 RAG 缓存。

2. 搜索文档：
   - 前端输入文档名关键词。
   - 后端查询 MySQL。
   - 返回文档名、切片数、预览内容和 `doc_key`。
   - 不返回服务器绝对路径。

3. 删除文档：
   - 使用 `doc_key` 定位文档。
   - 删除服务端文件。
   - 删除 MySQL 文档记录和条文记录。
   - 删除 Milvus 对应向量。
   - 刷新 RAG 缓存和 BM25 索引。

4. 重新向量化：
   - 先清理旧记录和旧向量。
   - 再写入新切片、新向量和新缓存。
   - 避免旧版本条文残留。

#### doc_key 是什么

`doc_key` 是服务器根据文档路径生成的安全标识。前端只拿到 `doc_key`，不能看到 `/home/...` 这种真实路径。用户删除或预览文档时，前端把 `doc_key` 发给后端，由后端映射到真实文件。

### 2.12 面试追问准备

#### 为什么要做引用可验证回答？

法律场景对准确性要求高，回答必须能追溯到具体法规文本。普通 RAG 只把检索文本塞进 prompt，用户看不到模型到底依据了哪条内容。我把检索结果结构化为 evidence，让模型只能引用系统给定编号，并在回答后做引用校验。

#### 为什么要做深度研究？

简单问答只适合直接问题。复杂法律问题需要从依据、条件、救济、风险多个角度分析，所以我把问题拆成多个子问题，多轮检索后再让 LLM 基于证据生成报告。

#### 为什么要用 Redis 做上下文？

聊天上下文读取频繁，如果每轮都查 MySQL 并拼接历史消息，性能和 token 都不理想。Redis 用来缓存近期上下文和摘要，MySQL 负责持久化，二者结合可以兼顾性能和可靠性。

#### 为什么不用只向量检索？

法律条文有很多精确关键词，例如“仲裁时效”“协商一致”“劳动报酬”。BM25 对关键词敏感，向量检索对语义相似敏感，两者融合比单一路径更稳。

#### SSE 相比 WebSocket 为什么更合适？

当前场景主要是服务端向客户端单向推送模型生成结果，不需要双向实时通信。SSE 基于 HTTP，实现简单，容易接入 FastAPI 和前端 Fetch 流读取，也方便保留原来的 `/api/chat` 兜底链路。
